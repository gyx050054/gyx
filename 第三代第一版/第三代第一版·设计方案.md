## 1. 模块架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                    Android App (kotlin-demo)                 │
│  田块│设备│天气│我的 (4个底部板块) + 告警红点 + 地图          │
└────────────┬──────────────────────────────────────┬──────────┘
             │ REST                                   │ REST
┌────────────▼──────────────────────┐      ┌─────────▼────────────┐
│  微服务端 task-service (:9300)     │      │  ThingsBoard (:8080) │
│  ├─ 认证（注册/改密）               │      │  ├─ 遥测存储(时序库)    │
│  ├─ 任务（一次性/每天，扫描执行）     │◄────►│  ├─ Device Profile   │
│  ├─ 告警规则翻译层（DB + TB配置）    │      │  │   Alarm Rules      │
│  ├─ 天气网关（Open-Meteo）          │      │  ├─ 告警实体/API       │
│  └─ 短信桩（预留）                  │      │  └─ RPC oneway       │
└────────────────┬──────────────────┘      └─────────▲────────────┘
                 │ MQTT/REST                        │ MQTT
                 ▼                                  ▼
        土壤墒情/温湿度/电动阀模拟器(32台) ──────────────┘
```

**高内聚低耦合原则：**

- 各能力（任务/告警/天气/短信）是微服务端独立模块，对外走统一 REST
- 告警判定与存储放 **TB**（TB 规则引擎自动评估遥测），微服务端只做"规则翻译"（用户表单 ↔ TB 配置），职责单一
- TB 负责告警产生/存储/展示 API，微服务端负责业务编排，互不纠缠

## 2. 功能一：浇水任务支持"每天自动浇水"

### 2.1 需求（用户视角）已确认

- 建任务可选：**一次性**（现有）或 **每天**（每天到点自动开浇、到时自动关）
- 任务管理页**特别标注"每天"**；每天任务**可取消**（取消=不再自动执行，历史保留）

### 2.2 tasks 表扩展（闹钟比喻）

把"每天定时浇水"想成一个**闹钟**，两组角色一看就懂：

- **任务本身 = 闹钟设置**：存**一条**，永远挂着（每天7点响、响15分钟）。任务列表里标"每天"。
- **每次实际浇水 = 闹钟响了一次**：每次执行记一条**流水**（今天7点浇了15分钟），是台账。
- **想看"昨天浇没浇/有没有因雨跳过"** → 看流水台账。
- **取消任务 = 删闹钟**：以后不再自动响；已响过的历史（流水）保留。

**落库（tasks 表新增字段）：**

| 字段                | 类型      | 默认     | 说明                                         |
| ----------------- | ------- | ------ | ------------------------------------------ |
| `repeatMode`      | VARCHAR | `ONCE` | `ONCE`=一次性 / `DAILY`=每天重复                  |
| `dailyHour`       | INT     | 可空     | （DAILY 用）每天几点开始，0-23                       |
| `durationMinutes` | INT     | 可空     | 持续分钟（DAILY 用；ONCE 已由 startTime/endTime 表示） |

> ONCE 任务沿用现有 startTime/endTime；DAILY 任务用 dailyHour+durationMinutes。为兼容与统一，DAILY 也可在落库时把"今天的 startTime/endTime"至少写initial一次，但真正的重复由 dailyHour 驱动。

**流水表 `task_runs`（新增，记录每天/每次实际执行）：**

| 字段                        | 类型        | 说明                                                        |
| ------------------------- | --------- | --------------------------------------------------------- |
| `id`                      | BIGINT PK | 流水 ID                                                     |
| `taskId`                  | BIGINT    | 对应 tasks 的 id（模板）                                         |
| `deviceId` / `deviceName` | VARCHAR   | 执行设备                                                      |
| `runDate`                 | DATE      | 执行日期（每天一条）                                                |
| `startTs` / `endTs`       | BIGINT    | 实际执行起止                                                    |
| `status`                  | VARCHAR   | PENDING / RUNNING / COMPLETED / **SKIPPED_WEATHER**（因雨跳过） |
| `action`                  | VARCHAR   | on/off                                                    |

### 2.3 每天任务调度

- 复用现有 `TaskScanScheduler`（每10秒扫描），扩展逻辑：

| 节点   | 触发条件                                                                            | 动作                                   |
| ---- | ------------------------------------------------------------------------------- | ------------------------------------ |
| 开浇   | `DAILY 且 status=PENDING/上次COMPLETED 且 now 小时 == dailyHour 且 toDate 无 task_runs` | 复核天气 → 发开阀 RPC → task_runs 记 RUNNING |
| 关浇   | RUNNING 且 `now-dailyHour ≥ durationMinutes`                                     | 发关阀 RPC → task_runs 置 COMPLETED      |
| 因雨跳过 | 到 dailyHour 前天气判断 ≥80%                                                          | 不发 RPC，task_runs 记 SKIPPED_WEATHER   |

- **避免重复**：每天同一 DAILY 任务只执行一次（按 `runDate + taskId` 查 task_runs 去重）

### 2.4 与天气联动

- **自动任务**（DAILY 或系统自动触发的 ONCE 定时）：预报 **1 小时后降雨概率 ≥80%** → 当天跳过，task_runs 标 `SKIPPED_WEATHER`，任务管理可见
- **手动任务**（用户当天主动设置/点按钮）：**不跳过**；创建时调天气接口，若降雨概率高则 App 提示"预报可能下雨，是否仍要浇？"

### 2.5 冲突检测（基础扩展）

- 一次性任务：原逻辑不变
- 每天任务：**同一设备只允许一条 DAILY**（避免一天两浇矛盾）；一次性任务若与某 DAILY 时段重叠，视同冲突拒建（除非用户确认覆盖——本版先做拒建，后续可加覆盖）

## 3. 功能二：土壤墒情检测机（+5台）

### 3.1 模拟器改造（soil_simulator.py）

现状：上报 `soilMoisture/soilTemperature`，每10分钟。改为：

| 键名             | 类型    | 单位  | 说明            |
| -------------- | ----- | --- | ------------- |
| `soilSalinity` | float | ppm | 土壤盐分          |
| `soilPh`       | float | —   | 土壤 pH（约 0-14） |

- 上报间隔：`SOIL_INTERVAL = 3600`（每1小时）
- 不可操作：`SUPPORTS_RPC=False`（保持）
- 模拟：盐分随机波动，pH 围绕中性小幅波动

### 3.3 start_all / tb_setup

- `tb_setup/provision_demo_tenant.py` 幂等预置 5 台墒情设备

### 3.4 App

- `DeviceType` 加 `SOIL_MOISTURE`
- 田块详情墒情机卡片：显示"盐分 X ppm / pH Y"，点击看历史曲线

## 4. 功能三：天气站

### 4.1 Open-Meteo 免费天气接口（已核实，无需key）

```
GET https://api.open-meteo.com/v1/forecast
    ?latitude={lat}&longitude={lon}
    &current=temperature_2m,weather_code,precipitation
    &hourly=precipitation_probability,temperature_2m,precipitation
    &forecast_hours=4
    &timezone=auto
```

返回（免费、无 key）：

- `current.temperature_2m`：当前气温（℃）
- `current.weather_code`：天气代码（WMO，映射晴/云/雨）
- `current.precipitation`：当前降水量（mm）
- `hourly.precipitation_probability`：**逐小时降雨概率（%）** ← 直接提供，满足"1小时后下雨"

### 4.2 微服务端天气网关

接口：`GET /api/weather?lat=..&lon=..`

- 内部调 Open-Meteo → 字段映射 → 缓存（10分钟）避免高频调用
- 返回：`{success, weatherDesc, temperature, precipitation, precipProb1h}`

### 4.3 App「天气」板块（底部第4个）

- 底部导航：**田块 / 设备 / 天气 / 我的**
- 天气板块展示：当前天气描述、气温、降水量、未来1小时降雨概率；天气联动提示（如"今日预报降雨概率80%，自动浇水任务已当日跳过"）
- 本版仅 App 内展示/推荐，不推送短信

### 4.4 短信桩（Stub）

- 微服务端 `MessageSender` 接口，`LogSmsSender` 把短信写日志/存表，不真发
- 预留 `SmsService` 抽象，上线替换为阿里云/腾讯云
- 本版触发点（桩）：告警生成、降雨高提示——只记录不花钱

## 5. 功能四：自定义告警（用 ThingsBoard）

### 5.1 方案定位（v2.1 已改变更：采用自研告警引擎）

> ⚠️ **v2.1 变更**：经用户拍板，告警改为**微服务端自研告警引擎**（非 ThingsBoard Alarm Rules）。
> 实现：`alarm_rules` 表存规则 → 微服务端 `AlarmService` 每 30 秒拉设备最新遥测判规则 → 命中建 `alarm_records`（ACTIVE→ACKNOWLEDGED→RESOLVED）→ App 通过 `/api/alarms/**` 展示红点/列表/确认/规则管理。
> **§5.2-5.7 的 ThingsBoard Alarm Rules 方案不再采用**，保留作为"当时评估过的备选"，仅供参考。

**告警判定、产生、存储、展示全部由微服务端自研引擎完成**（依赖 ThingsBoard 仅作遥测存取），规则存 MySQL `alarm_rules` 表，按租户隔离。

### 5.2 ThingsBoard 自定义告警能力（当时评估，v2.1 起不采用）

** Device Profile Alarm Rules（1.0，v4.0.1 CE 支持）**

- 每个设备配置文件可配多条告警规则，每条 = 属性键 + 比较符 + 阈值 + 严重级别 + 清除条件
- 例：`temperature > 35 → CRITICAL`，`温度回落到 ≤35 → 自动清除`
- **单键阈值告警**：官方文档明确"用 Device Profile Alarm Rules 配置最少最合适"

** Dynamic 动态阈值**

- 阈值可设为从设备 **server attribute** 取值（Dynamic 源）
- 微服务端改属性值 = 改阈值，运行时生效，无需动规则

** 完整告警生命周期与 API**

- 状态：`Active Unacknowledged → Active Acknowledged → Cleared`
- REST API：查询告警、未确认数量、确认(ack)、管理——App 直接用

### 5.3 架构（规则翻译层）

```
App 用户配规则
   │ REST
   ▼
微服务端 规则翻译层
   ├─ 存规则到 MySQL alarm_rules（用户友好的表单：设备类型+属性+比较符+阈值+级别）
   └─ 同步到 TB：
       ① Device Profile 的 alarmRules（阈值类：盐分>X、气温>Y、水压==0、电量<Z）
       ② 设备的 server attribute（Dynamic 阈值，用户改阈值即改属性值）
   ▼
TB 规则引擎自动评估遥测 → 自动创建/清除告警
   ▼
App 调 TB 告警 API → 红点 / 列表 / 确认 / 恢复
```

**跨设备扩展**：新设备类型 = 新建 Device Profile + 配其 alarmRules，天然支持"以后加各种设备"

### 5.4 数据模型

**表 `alarm_rules`（微服务端，用户表单持久化 + 同步源）**

| 字段             | 类型        | 说明                                                                       |
| -------------- | --------- | ------------------------------------------------------------------------ |
| `id`           | BIGINT PK | 规则 ID                                                                    |
| `tenantId`     | VARCHAR   | 归属租户                                                                     |
| `deviceType`   | VARCHAR   | VALVE / TEMPERATURE_HUMIDITY / SOIL_MOISTURE（可扩展）                        |
| `attributeKey` | VARCHAR   | 属性键：soilSalinity / soilPh / temperature / waterPressure / batteryLevel 等 |
| `operator`     | VARCHAR   | > 、>= 、< 、<= 、== 、!=                                                     |
| `threshold`    | FLOAT     | 阈值                                                                       |
| `severity`     | VARCHAR   | MINOR / MAJOR / CRITICAL                                                 |
| `alarmType`    | VARCHAR   | 告警类型名，如 SOIL_SALINITY_HIGH                                               |
| `enabled`      | BOOLEAN   | 是否启用                                                                     |
| `createdAt`    | LONG      | 创建时间                                                                     |

**告警记录与状态流转放 TB**（用 TB 告警实体，不另建表）。App 查 `GET /api/alarm*`。

### 5.5 四类示例（要落地的规则）

| 需求        | Device Profile Alarm Rule 配置                |
| --------- | ------------------------------------------- |
| 土壤水分低于 X% | 属性 `soilMoisture < X` → MINOR/MAJOR，清除：≥X   |
| 气温高于 X℃   | 属性 `temperature > X` → MAJOR/CRITICAL，清除：≤X |
| 电动阀水压 = 0 | 属性 `waterPressure == 0` → CRITICAL，清除：>0    |
| 剩余电量低于 X% | 属性 `batteryLevel < X` → MINOR，清除：≥X         |

阈值用 **Dynamic（server attribute）**，用户改 App 规则 → 微服务端更新设备属性 → 生效。

### 5.6 注意（v4.0.1 限制）

- 你的 TB 是 **v4.0.1 CE**：支持 Device Profile Alarm Rules **1.0**（单键阈值告警），覆盖本版全部需求
- **Alarm Rules 2.0**（多信号组合/Missing For）需 **4.3+**，v4.0.1 用不了；本版也不需
- 动态阈值在 v4.0.1 支持（官方文档 Example 为证）

### 5.7 告警 App 交互

- 顶栏铃铛 + 红点（`unread-count > 0` 亮）
- 告警列表：级别色标（MINOR=黄/MAJOR=橙/CRITICAL=红）、设备、实测值、时间、确认按钮
- 确认后红点消失；条件恢复后自动标"已恢复"
- 规则管理页（管理员）：增删改查 + 启用开关；新建选 设备类型→属性→比较符→阈值→级别

## 7. 风险与容错

| 风险                         | 应对                          |
| -------------------------- | --------------------------- |
| Open-Meteo 国内访问不稳          | 超时+降级（返回"天气暂不可用"）；可加备用源     |
| TB alarmRules 1.0 无法处理组合条件 | 本版需求均为单键阈值，够用；组合条件等 4.3+ 再说 |
| DAILY 跨天/时区                | 用服务器本地时间 + 配置时区             |
| 地图瓦片量大                     | 只加载可见区域 + 本地缓存              |
| 短信桩被误当已真发                  | 桩实现打日志，明确标注"未接入真实短信"        |
